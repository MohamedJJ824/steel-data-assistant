# Data card

Two public datasets, plus a thin synthetic layer that links them. Nothing here
comes from a real company's systems.

---

## 1. Real data

### 1.1 Steel Industry Energy Consumption — `plant.energy_readings`

| | |
|---|---|
| Source | UCI Machine Learning Repository, id **851** |
| URL | https://archive.ics.uci.edu/dataset/851 |
| Origin | A steel company in Gwangyang, South Korea |
| Licence | CC BY 4.0 (as published by UCI) |
| Rows loaded | **35,040** — exactly one per 15-minute interval of 2018 |
| Columns | 11, all non-null |
| Coverage | `2018-01-01 00:00:00` to `2018-12-31 23:45:00` |

Transformations applied on load:

- Column names lowercased to snake_case (`Usage_kWh` → `usage_kwh`,
  `CO2(tCO2)` → `co2_tco2`, `Lagging_Current_Reactive.Power_kVarh` →
  `lagging_current_reactive_power_kvarh`).
- `date` parsed with the explicit format `%d/%m/%Y %H:%M`. The source is
  **day-first**, confirmed by inspection: the first field reaches 31 while the
  second never exceeds 12.
- Rows sorted by timestamp. The source file is **not** in chronological order:
  each day's block runs `00:15 … 23:45` and then a `00:00` row that closes the
  day out, so the label marks the **end** of each interval.
- Read as `utf-8-sig`; the served file carries a UTF-8 BOM.

No values were altered, filtered or imputed.

### 1.2 Steel Plates Faults — `plant.plate_inspections`

| | |
|---|---|
| Source | UCI Machine Learning Repository, id **198** |
| URL | https://archive.ics.uci.edu/dataset/198 |
| Origin | Semeion, Research Center of Sciences of Communication, Rome |
| Licence | CC BY 4.0 (as published by UCI) |
| Rows loaded | **1,941** |
| Columns | 27 measurements + 7 one-hot fault flags |

Transformations applied on load:

- The 7 one-hot fault columns collapse into a single `fault_code`. Verified
  safe: all 1,941 rows have exactly one flag set.
- `TypeOfSteel_A300` / `TypeOfSteel_A400` collapse into `steel_grade`
  (`A300` / `A400`). Also exactly one per row.
- `plate_id` assigned as a 1-based sequential index in source file order. The
  source has no identifier of its own.

**The fault code is `K_Scratch`, not `K_Scatch`.** The misspelling circulates
in secondary mirrors of this dataset; the UCI API payload spells it correctly.

Observed fault distribution:

| fault_code | plates |
|---|---|
| Other_Faults | 673 |
| Bumps | 402 |
| K_Scratch | 391 |
| Z_Scratch | 190 |
| Pastry | 158 |
| Stains | 72 |
| Dirtiness | 55 |

## 2. Synthetic data

The two public datasets share no key. Everything in this section was fabricated
to make cross-table questions possible. It is generated by
`scripts/load_db.py` and `scripts/generate_synthetic_tables.py` with global
seed **42**, and is reproducible byte-for-byte.

**None of it describes any real plant, person or event.**

### 2.1 `plant.production_lines` — fully synthetic (3 rows)

| line_id | name_en | process | commissioned_year |
|---|---|---|---|
| L1 | Hot rolling line | hot_rolling | 2005 |
| L2 | Cold rolling line | cold_rolling | 2011 |
| L3 | Finishing and inspection line | finishing | 2016 |

### 2.2 `plant.shifts` — fully synthetic (3 rows)

A standard 3×8 pattern: `M` 06:00–14:00, `A` 14:00–22:00, `N` 22:00–06:00.
The night shift wraps past midnight, which any per-shift query must handle.

### 2.3 `plant.fault_types` — codes real, attributes synthetic (7 rows)

`fault_code` values are the genuine UCI column names. `label_fr`, `label_en`,
`severity` (1–3) and `procedure_doc_id` are invented. Severity assignments:

| fault_code | severity | procedure_doc_id |
|---|---|---|
| Z_Scratch | 3 | PROC-FLT-ZSCR |
| K_Scratch | 3 | PROC-FLT-KSCR |
| Pastry | 2 | PROC-FLT-PAST |
| Bumps | 2 | PROC-FLT-BUMP |
| Other_Faults | 2 | PROC-FLT-OTHR |
| Stains | 1 | PROC-FLT-STAI |
| Dirtiness | 1 | PROC-FLT-DIRT |

Severity drives the quality-hold rules in `corpus/legacy_code/quality_hold.py`,
so these values are load-bearing and must not be changed casually.

### 2.4 `plant.plate_inspections` — two synthetic columns added

| column | how it was generated |
|---|---|
| `line_id` | Drawn per plate from a fault-dependent distribution over L1/L2/L3. Hot rolling is weighted towards `Bumps` and `Pastry`, cold rolling towards `Z_Scratch` and `K_Scratch`, finishing towards `Stains` and `Dirtiness`. The weights are deliberately uneven so that "which line has the most X" has one defensible answer. |
| `inspected_at` | A uniform day in 2018 with the hour drawn from a day-shift-weighted distribution (06:00–22:00 roughly 3× as likely as night hours). |

Resulting plates per line: L1 721, L2 753, L3 467.

The 27 measurement columns and `fault_code` are untouched real data.

### 2.5 `plant.maintenance_events` — fully synthetic (300 rows)

| column | how it was generated |
|---|---|
| `event_id` | Sequential from 1001. |
| `line_id` | Uniform over L1/L2/L3. |
| `started_at` | Same day-shift-weighted 2018 distribution as inspections, sorted ascending. |
| `category` | 40% `preventive`, 60% `corrective`. |
| `fault_code` | `NULL` for preventive. For corrective, drawn in proportion to how often each fault actually occurs in the inspection data. |
| `downtime_minutes` | Lognormal with a severity-dependent mean (severity 1 → 35 min, 2 → 70 min, 3 → 165 min; preventive → 45 min), σ = 0.55, clamped to [10, 600] so one freak draw cannot dominate the yearly totals. |
| `ended_at` | `started_at + downtime_minutes`, so the three columns are always consistent. |
| `report_doc_id` | Set on the **20 longest corrective events** only, as `MNT-RPT-<event_id>`. The remaining 280 have `NULL`: not every intervention gets written up, and the agent should be able to say a report does not exist. |

Resulting downtime by fault (corrective only):

| fault_code | events | total minutes |
|---|---|---|
| K_Scratch | 42 | 8,837 |
| Other_Faults | 65 | 4,736 |
| Z_Scratch | 17 | 4,063 |
| Bumps | 34 | 3,125 |
| Pastry | 14 | 1,103 |
| Dirtiness | 6 | 403 |
| Stains | 6 | 258 |

### 2.6 Document corpus — `corpus/docs/` (milestone 2)

French markdown, generated from templates with facts injected from the database
so documents and SQL cannot disagree. Fictional roles only, no names.

The peak-load policy's alert threshold is the 95th percentile of `usage_kwh`
over the real data: **99.04 kWh**, written as **99 kWh** in prose.

### 2.7 Legacy code corpus — `corpus/legacy_code/` (milestone 2)

A simulated plant analytics codebase, written for this project. It is data to
be searched, not part of the running application.
